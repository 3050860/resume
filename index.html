Problems I have solved

Server memory footprint −98%

Symptom
A C++ server held 5.2 GB of resident memory; nobody knew why.
Root cause
Transparent Huge Pages were enabled and glibc created far more malloc arenas than the workload needed, so freed memory was never returned to the OS.
Fix
Tuned the allocator and THP policy for the process.
Result
RSS dropped from 5,200 MB to 105 MB.

Server crashed when thousands of TVs connected at once

Symptom
A production server segfaulted with a corrupted stack during connection storms. A standalone stress test of the same code never crashed, even under AddressSanitizer.
Root cause
Ran the real server with an ASan build of the library: select() was used to wait for a non-blocking connect. With thousands of open sockets the new descriptor number exceeded FD_SETSIZE (1024), and FD_SET wrote past the fd_set on the stack. The test program had too few descriptors to hit it. While there, found a race between two concurrent connect() calls to the same address.
Fix
Switched to poll(); made the address check and registration atomic. Added regression tests that open 1,100 extra descriptors and run a 16-thread connect storm.
Result
3,400 emulated TVs connecting and reconnecting three times, 2,905 device checks: no crash, no ASan reports. Before the fix it crashed within the first four connections. Concurrent connects went from 10–14 s to 10–100 ms.

One slow client stalled the whole fleet

Symptom
When a single device on a bad link slowed down, every other device stopped being served.
Root cause
The legacy in-house protocol processed one shared read queue, so one slow peer blocked all the rest (head-of-line blocking).
Fix
Rewrote the protocol layer so each peer is handled independently, keeping wire compatibility with devices already deployed.
Result
Slow devices no longer affect others; old clients kept working without an update.

Embedded web server 25× faster, 60× leaner

Fix
Reworked buffering and configuration of the built-in HTTP server.
Result
Throughput from 3 MB/s to 75 MB/s while using 60 times less memory.

Shutdown that never finished

Symptom
On SIGINT, modules hung waiting for network downloads; restarts took unpredictably long. The server also had memory leaks and thread deadlocks.
Fix
Hunted down the leaks and deadlocks; added explicit timeouts to every module so all of them exit within a fixed deadline.
Result
Stable long-running server with predictable restarts.

Latency spikes in memcached

Symptom
Responses of certain sizes came back with a large, constant delay.
Root cause
The TCP_NODELAY socket option was not set, so Nagle's algorithm held back small packets.
Result
Patched and deployed in our production; the delay disappeared.

Thread leak in an open-source Java push server

Symptom
A push server with thousands of connected browsers slowly leaked threads. The team assumed the bug was in our callbacks.
Root cause
Found by reading the server's source: a thread counter shared between threads was not declared volatile.
Result
One-word fix; the leak was gone.
